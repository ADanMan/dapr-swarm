# Swarm — локальный рой

Этот skill и клиент `scripts/swarm.py` привязаны к релизу **v0.4.1** репозитория `ADanMan/dapr-swarm`. Установщик извлекает их из Git-тега, записывает commit и SHA-256 в `RELEASE.json`. Используй приложенный клиент, а не произвольную версию `swarm` из PATH. Он не требует сторонних Python-пакетов, ключей или входа в Codex.

Для установленного skill команда выглядит так (если Hermes показал другой путь skill, используй его):

```bash
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json health
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json submit --prompt-file /absolute/task.md --file /absolute/input.txt --commands 1000 --command-reserve 100 --work-window 16
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json show TASK_ID
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json events TASK_ID
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json files TASK_ID
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json wait TASK_ID --deadline 45
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json download TASK_ID outputs/final-answer.md --output /absolute/new-answer.md
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json stop TASK_ID
python3 ~/.hermes/skills/swarm/scripts/swarm.py --json resume TASK_ID
```

Глобальные параметры `--json`, `--timeout` и `--base-url` ставь перед командой. По умолчанию API — `http://127.0.0.1:8788`. Если сервис недоступен, запусти `start.command` из своей папки клонированного репозитория и проверь health. Не открывай `.env`, не меняй маршрутизацию моделей и не копируй ключи.

Для контроля ресурсов агенты используют `get_budget`. Для JSON-массивов отдельную запись можно прочитать через `read_file(path="inputs/batch.json", json_key="case_id", json_value="C001")`; не передавай каждому исполнителю весь набор данных. Новые задачи используют профиль рассуждения `low` и обязательную проверку артефактов. Обрезанный ответ `finish_reason=length` не исполняется: runtime ограниченно повторяет шаг с увеличенным лимитом ответа и требованием сократить действие. Если попытки исчерпаны, проверь сохранённые файлы и продолжи незавершённый этап; не пересоздавай готовые результаты.

## Постановка задачи

Включи цель, входные данные, ожидаемые файлы и критерии готовности. Передавай только относящиеся к задаче файлы, разрешённые пользователем. Большой текст запиши в UTF-8 файл и передай через `--prompt-file`; не вставляй пользовательский текст в shell-код. Сохрани возвращённый ID и дай ссылку `http://127.0.0.1:8788/#TASK_ID`.

По умолчанию задача получает 2000 дочерних агентов и 20000 обращений GLM, включая повторы. Это лимиты на задачу, не число одновременных запросов. Все роли используют GLM. Новые задачи отклоняют `--allow-codex`. Координатор и руководители направлений обязаны делегировать; исследователи, аналитики, программисты и проверяющие также могут создавать дочерних агентов. Глубина — до 5, бюджеты общие на всё дерево. Поручай цель с критериями и разрешай независимые направления выполнять параллельно. Для большого задания укажи независимые единицы работы, уникальные пути результатов и порядок сборки и проверки. Лимиты — потолок, а не цель: не создавай агентов для расходования квоты. Интернет-поиск выполняется инструментами SearXNG роя и не требует Codex. Локальные команды изолированы: Python со стандартной библиотекой, без shell-сети и установки пакетов. Пределы количества агентов не означают столько же одновременных запросов; текущая параллельность GLM — 8.

## Планирование ограниченной работы

Перед запуском раздели бюджет GLM, число агентов и локальные команды. Чтение и запись файлов, поиск и выполнение команд — разные инструменты: расход команд нельзя оценить по числу агентов или файлов. Для однотипных результатов задавай общий формат и ссылки на входные файлы, избегай копирования полного корпуса в каждое поручение. Назначай отдельные пути исполнителям; не допускай одновременной записи в один файл.

Параметры `submit`: `--commands` — общий лимит локальных команд (по умолчанию 1000, диапазон 1–20000); `--command-reserve` — часть этого лимита для роли `swarm_reviewer` (100, от 0 до лимита минус 1); `--work-window` — окно допущенных к работе специалистов (16, диапазон 1–64). Резерв не добавляет команды поверх общего лимита: остальные роли его расходовать не могут. Назначай итоговый запуск проверки проверяющему. При малом `--commands` явно снизь резерв, чтобы он оставался меньше лимита. Перед делегированием и командами поручай агентам проверять текущий остаток бюджета доступным инструментом.

Окно ограничивает одновременно допущенные workflow специалистов; ожидающий детей родитель освобождает своё место, чтобы вложенная работа могла продолжиться. Ожидание допуска не является ошибкой. Окно 16 не означает 16 HTTP-запросов: лимит GLM остаётся 8. Сохраняй общий план большого задания, выполняя его волнами, а не снижая количество требуемых результатов.

План должен доводить ограниченные группы до артефактов и проверок, затем открывать следующую группу. Сохрани ресурс для сборки, независимой проверки и исправлений. Не проси каждого листового агента запускать одинаковую локальную команду: чтение через `read_file` и запись через `write_file` не требуют `run_command`. Команда проверки должна читать фактические результаты и проверять критерии, а не печатать заранее заданное «успешно».

## Автоматическая приёмка и восстановление

Координатор поручает финальную приёмку отдельному `swarm_reviewer`, созданному непосредственно корнем задачи. Проверяющий сначала завершает отчёты и исправления, затем последним действием выполняет `run_validation(command=..., artifact_paths=["outputs"], criteria=[...])`. Команда должна реально проверять критерии и возвращать ненулевой exit code при нарушении. После проверки нельзя менять артефакты: runtime хранит состав и SHA-256 всего outputs и помечает запись устаревшей при изменениях. Служебные outputs/.codex-tmp и автоматически создаваемый final-answer.md исключены из обхода каталога. Проверяющие отдельных групп используют `run_command` и передают выводы; частичная проверка не является приёмкой всей цели.

В `show --json` смотри `acceptance.status`: unverified, checking, passed, failed, stale. GUI автоматически показывает ту же запись, критерии, команду, exit code, хеши и источник. Passed подтверждает успешное выполнение зарегистрированной проверки неизменённых артефактов, но не доказывает семантическую полноту произвольного проверяющего скрипта. Не заменяй запись словами «ПРИНЯТО» из ответа модели.

Новые задачи автоматически продолжаются после исчерпания локальных повторов подтверждённых временных ошибок модели: nginx401, 429/5xx, сеть, таймаут, пустой или обрезанный ответ. Не более трёх продолжений с паузами 15/60/180 секунд. Внутри одной цели создаётся новый связанный запуск с файлами; ему доступны только оставшиеся агенты, вызовы и команды, резерв проверки также пересчитывается. Настоящий отказ ключа, исчерпанный бюджет, ошибка кода и Stop не вызывают автоматическое продолжение. Исторические задачи при обновлении не запускаются сами.

При `recovery.status=scheduled` дождись времени `retry_at`, при continued следуй `next_task_id`. Не вызывай ручной resume поверх ожидающего восстановления: он предназначен для явного нового запуска и возвращает полный прежний бюджет. `wait` автоматически ждёт scheduled и следует автоматическим продолжениям в пределах единого deadline, не выполняя POST. Stop отменяет ожидание и останавливает последнюю связанную попытку. Если восстановление blocked/exhausted, сообщи причину; не обходи ограничение бесконечными ручными resume.

## Контроль результата

`wait`: 0 — завершено, 1 — ошибка/остановка, 3 — истёк срок ожидания, 130 — Ctrl-C. Таймаут ожидания и Ctrl-C не останавливают удалённую задачу. После таймаута продолжай следить за тем же ID; не создавай дубликат. При ошибке submit без однозначного ответа проверь list и текст/время задачи до повторной отправки. Автоматических POST-повторов нет.

Статус completed и код 0 у `wait` означают завершение workflow, а не независимую приёмку результата. Прочитай итог, проверь наличие и содержимое нужных файлов, фактические exit code и вывод проверок. Укажи отдельно выполненную работу, проверенные критерии и ограничения. Если проверка не выполнена, так и сообщи; не называй непроверенный результат принятым.

Число созданных агентов показывает структуру работы. Оно не доказывает число готовых файлов, их корректность или одновременное исполнение HTTP-запросов. Для сотен агентов проверяй отдельные ветви и их родителей в GUI «План и команда»; используй «Файлы» и «Журнал» для артефактов и ошибок. Для поиска среди сотен агентов используй роль или ID и фильтр «Только проблемы»; ветви сгруппированы по родителям. В «Обзоре» проверь остатки команд для работы и проверки. Статус ветви — состояние workflow, а не оценка качества её ответа. Не считай число всех файлов числом готовых результатов: в нём могут быть входы и заметки.

`events` показывает до 250 последних событий, не полный транскрипт. Запись через `run_command` не обязана иметь отдельное событие `file`; неполная история не доказывает авторство каждого файла. Скачивание не перезаписывает существующий файл. Для нагрузочной приёмки сохраняй ID, параметры, артефакты и независимый протокол; локальные исторические испытания не входят в публичный репозиторий и не доказывают качество конкретного нового запуска. Тысячи одновременно работающих агентов не подтверждены нагрузочным тестом.

Ручной resume используй только при отсутствии ожидающего автоматического продолжения. Возобновляй failed/stopped по просьбе пользователя или когда продолжение уже входит в порученную работу. resume возвращает **новый ID** связанного запуска с файлами и недавним контекстом. Исходная история сохраняется; счётчики нового запуска начинаются с нуля при прежних лимитах, резерве и окне работы. Старые задачи сохраняют настройки 100 команд, без резерва и без окна; `resume` не переводит их автоматически на новые значения. Если причиной остановки был прежний недостаточный бюджет, повтор с теми же настройками может снова остановиться: для новых параметров создай явно отдельную задачу с нужными входами и проверенными промежуточными файлами. Повтор resume для одного исходного ID возвращает то же продолжение. Дальше отслеживай новый ID. Это не восстановление команды посередине и не исправление upstream-сбоя BeeGate. Перед возобновлением установи причину остановки и проверь, что сохранённые результаты позволяют продолжить. Не запускай бесконечную цепочку возобновлений при одной и той же ошибке; сообщи устойчивую причину остановки. Сохраняй исходные провалы и отчёты: новый запуск не превращает предыдущий в успешный. Не повышай исчерпанный бюджет задним числом для объявления приёмки.
